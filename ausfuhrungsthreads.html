    10. Ausführungsthreads

    10.1. Die Klasse „Thread“

    Wenn eine Anwendung gestartet wird, wird sie in einem Ausführungsstrom ausgeführt, der als Thread bezeichnet wird. Die Klasse .NET, die einen Thread modelliert, ist die Klasse System.Threading.Thread und hat folgende Definition:

    Konstruktoren

    In den folgenden Beispielen werden wir ausschließlich die Konstruktoren von [1,3] verwenden. Der Konstruktor [1] akzeptiert als Parameter eine Methode mit der Signatur [2], c.a.d, die einen Parameter vom Typ object hat und kein Ergebnis zurückgibt. Der Konstruktor [3] akzeptiert als Parameter eine Methode mit der Signatur [4] oder c.a.d, die keinen Parameter hat und kein Ergebnis zurückgibt.

    Eigenschaften

    Einige nützliche Eigenschaften:

    • Thread CurrentThread: statische Eigenschaft, die eine Referenz auf den Thread liefert, in dem sich der Code befindet, der diese Eigenschaft angefordert hat
    • string Name: Der Name des Threads
    • bool IsAlive: Gibt an, ob der Thread gerade ausgeführt wird oder nicht.

    Methoden

    Die am häufigsten verwendeten Methoden sind die folgenden:

    • Start(), Start(object obj): Startet die asynchrone Ausführung des Threads und übergibt ihm gegebenenfalls Informationen in einem Typ object.
    • Abort(), Abort(object obj): zum erzwungenen Beenden eines Threads
    • Join(): Der Thread T1, der T2.Join ausführt, wird blockiert, bis der Thread T2 beendet ist. Es gibt Varianten, um das Warten nach einer bestimmten Zeit zu beenden.
    • Sleep(int n): statische Methode – der Thread, der die Methode ausführt, wird für n Millisekunden angehalten. Er verliert dabei die Prozessorausführung, die einem anderen Thread zugewiesen wird.

    Sehen wir uns eine erste Anwendung an, die die Existenz eines Hauptausführungsthreads verdeutlicht, in dem die Funktion Main einer Klasse ausgeführt wird:

    
using System;
using System.Threading;

namespace Chap8 {
    class Program {
        static void Main(string[] args) {
            // Initialisierung des aktuellen Threads
            Thread main = Thread.CurrentThread;
            // Anzeige
            Console.WriteLine("Thread courant : {0}", main.Name);
            // Name wird geändert
            main.Name = "main";
            // Überprüfung
            Console.WriteLine("Thread courant : {0}", main.Name);

            // Endlosschleife
            while (true) {
                // Anzeige
                Console.WriteLine("{0} : {1:hh:mm:ss}", main.Name, DateTime.Now);
                // vorübergehende Unterbrechung
                Thread.Sleep(1000);
            }//while        
        }
    }
}

    • Zeilen 10–14: Sein Name wird angezeigt und geändert
    • Zeilen 17–22: Eine Schleife, die jede Sekunde eine Anzeige durchführt
    • Zeile 21: Der Thread, in dem die Methode [main] ausgeführt wird, wird für 1 Sekunde angehalten

    10.2. Erstellung von Ausführungsthreads

    Es gibt Anwendungen, bei denen Codeabschnitte „gleichzeitig“ in verschiedenen Ausführungsthreads ausgeführt werden. Wenn man sagt, dass threads gleichzeitig ausgeführt werden, handelt es sich oft um eine sprachliche Ungenauigkeit. Verfügt der Rechner nur über einen Prozessor – was nach wie vor häufig der Fall ist –, teilen sich die threads diesen Prozessor: Sie haben abwechselnd für einen kurzen Moment (einige Millisekunden) Zugriff darauf. Dies erzeugt die Illusion einer parallelen Ausführung. Die einem thread zugewiesene Zeit hängt von verschiedenen Faktoren ab, darunter seine Priorität, die einen Standardwert hat, aber auch programmgesteuert festgelegt werden kann. Wenn ein thread über den Prozessor verfügt, nutzt er diesen normalerweise während der gesamten ihm zugewiesenen Zeit. Er kann ihn jedoch vorzeitig freigeben:

    • indem es auf ein Ereignis wartet (Wait, Join)
    • indem er für eine bestimmte Zeit in den Ruhezustand wechselt (Sleep)
    1. Ein Thread T wird zunächst durch einen der oben vorgestellten Konstruktoren erstellt, zum Beispiel: 
    Thread thread=new Thread(Start);

    wobei Start eine Methode mit einer der beiden folgenden Signaturen ist:

    void Start();
void Start(object obj);

    Die Erstellung eines Threads führt nicht zu dessen Start.

    1. Die Ausführung des Threads T wird durch T.Start() gestartet: Die an den Konstruktor von T übergebene Methode Start wird dann vom Thread T ausgeführt. Das Programm, das die Anweisung T.Start() ausführt, wartet nicht auf das Ende der Aufgabe T: Es springt sofort zur nächsten Anweisung. Es laufen also zwei Aufgaben parallel ab. Oft müssen sie miteinander kommunizieren können, um zu erfahren, wie weit die gemeinsam auszuführende Arbeit fortgeschritten ist. Dies ist das Problem der Thread-Synchronisation.
    2. Einmal gestartet, läuft der Thread T autonom ab. Er wird beendet, sobald die von ihm ausgeführte Methode Start ihre Arbeit beendet hat.
    3. Man kann den Thread T zwingen, zu enden:
      1. T.Abort() weist den Thread T an, sich zu beenden.
    4. Man kann auch mit T.Join() auf das Ende seiner Ausführung warten. Hierbei handelt es sich um eine blockierende Anweisung: Das Programm, das sie ausführt, wird blockiert, bis die Aufgabe T ihre Arbeit beendet hat. Dies ist eine Möglichkeit der Synchronisation.

    Betrachten wir das folgende Programm:

    
using System;
using System.Threading;

namespace Chap8 {
    class Program {
        public static void Main() {
            // aktuellen Thread initialisieren
            Thread main = Thread.CurrentThread;
            // Thread mit einem Namen versehen
            main.Name = "Main";

            // Erstellung von Ausführungsthreads
            Thread[] tâches = new Thread[5];
            for (int i = 0; i < tâches.Length; i++) {
                // Thread i wird erstellt
                tâches[i] = new Thread(Affiche);
                // Der Name des Threads wird festgelegt
                tâches[i].Name =  i.ToString();
                // Start der Ausführung des Threads i
                tâches[i].Start();
            }

            // Ende der Hauptschleife
            Console.WriteLine("Fin du thread {0} à {1:hh:mm:ss}",main.Name,DateTime.Now);
        }

        public static void Affiche() {
            // Anzeige des Ausführungsbeginns
            Console.WriteLine("Début d'exécution de la méthode Affiche dans le Thread {0} : {1:hh:mm:ss}",Thread.CurrentThread.Name,DateTime.Now);
            // 1 Sekunde lang in den Ruhezustand versetzen
            Thread.Sleep(1000);
            // Anzeige des Endes der Ausführung
            Console.WriteLine("Fin d'exécution de la méthode Affiche dans le Thread {0} : {1:hh:mm:ss}", Thread.CurrentThread.Name, DateTime.Now);
        }
    }
}

    • Zeilen 13–21: Es werden 5 Threads erstellt und ausgeführt. Die Referenzen der Threads werden in einem Array gespeichert, um sie später wieder abrufen zu können. Jeder Thread führt die Methode Affiche aus den Zeilen 27–35 aus.
    • Zeile 20: Der Thread Nr. i wird gestartet. Dieser Vorgang ist nicht blockierend. Der Thread Nr. i wird parallel zu dem Thread der Methode [Main] ausgeführt, der ihn gestartet hat.
    • Zeile 24: Der Thread, der die Methode [Main] ausführt, wird beendet.
    • Zeilen 27–35: Die Methode [Affiche] führt Ausgabevorgänge durch. Sie gibt den Namen des Threads aus, der sie ausführt, sowie die Start- und Endzeit der Ausführung.
    • Zeile 31: Jeder Thread, der die Methode [Affiche] ausführt, wird für 1 Sekunde angehalten. Der Prozessor wird dann an einen anderen Thread übergeben, der auf den Prozessor wartet. Nach Ablauf der 1-Sekunden-Pause wird der angehaltene Thread wieder als Kandidat für den Prozessor in Betracht gezogen. Er erhält den Prozessor, sobald er an der Reihe ist. Dies hängt von verschiedenen Faktoren ab, darunter die Priorität der anderen Threads, die auf den Prozessor warten.

    10.3. Vorteile von Threads

    Nachdem wir nun die Existenz eines Standard-Threads aufgezeigt haben – nämlich den, der die Methode Main ausführt – und wissen, wie man weitere erstellt, wollen wir uns nun mit dem Nutzen von Threads für uns und den Gründen befassen, warum wir sie hier vorstellen. Es gibt eine Art von Anwendungen, die sich gut für den Einsatz von Threads eignen: Client-Server-Anwendungen im Internet. Diese werden wir im folgenden Kapitel vorstellen. In einer Client-Server-Anwendung im Internet beantwortet ein Server auf einem Rechner S1 Anfragen von Clients auf entfernten Rechnern C1, C2, ..., Cn.

    Wir nutzen täglich Internetanwendungen, die diesem Schema entsprechen: Webdienste, E-Mail, Forenbesuche, Dateiübertragungen … Im obigen Schema muss der Server S1 die Clients Ci gleichzeitig bedienen. Nehmen wir das Beispiel eines Servers FTP (File Transfer Protocol), der Dateien an seine Clients ausliefert. Wir wissen, dass eine Dateiübertragung manchmal mehrere Minuten dauern kann. Es kommt natürlich nicht in Frage, dass ein einzelner Client den Server während einer solchen Zeitspanne allein beansprucht. Üblicherweise erstellt der Server so viele Ausführungs-Threads, wie es Clients gibt. Jeder Thread ist dann dafür zuständig, sich um einen bestimmten Client zu kümmern. Da der Prozessor zyklisch zwischen allen aktiven Threads des Rechners aufgeteilt wird, verbringt der Server ein wenig Zeit mit jedem Client und gewährleistet so die Parallelität des Dienstes.

    In der Praxis nutzt der Server einen Thread-Pool mit einer begrenzten Anzahl von Threads, beispielsweise 50. Der 51. Client wird dann gebeten, zu warten.

    10.4. Informationsaustausch zwischen Threads

    In den vorangegangenen Beispielen wurde ein Thread wie folgt initialisiert:

    Thread t=new Thread(Run);

    wobei Run eine Methode mit folgender Signatur war:

    void Run();

    Es ist auch möglich, die folgende Signatur zu verwenden:

    void Run(object obj);

    Dadurch können Informationen an den gestarteten Thread übermittelt werden. So

    t.Start(obj1);

    wird der Thread t gestartet, der dann die Methode Run ausführt, die ihm konstruktionsbedingt zugeordnet wurde, wobei ihm der effektive Parameter obj1 übergeben wird. Hier ein Beispiel:

    
using System;
using System.Threading;

namespace Chap8 {
    class Program4 {
        public static void Main() {
            // aktuellen Thread initialisieren
            Thread main = Thread.CurrentThread;
            // Dem Thread wird ein Name zugewiesen
            main.Name = "Main";

            // Erstellung von Ausführungsthreads
            Thread[] tâches = new Thread[5];
            Data[] data = new Data[5];
            for (int i = 0; i < tâches.Length; i++) {
                // Erstellung des Threads i
                tâches[i] = new Thread(Sleep);
                // Festlegen des Thread-Namens
                tâches[i].Name = i.ToString();
                // Start der Ausführung von Thread i
                tâches[i].Start(data[i] = new Data { Début = DateTime.Now, Durée = i+1 });
            }
            // Warten auf alle Threads
            for (int i = 0; i < tâches.Length; i++) {
                // Warten auf das Ende der Ausführung von Thread i
                tâches[i].Join();
                // Anzeige des Ergebnisses
                Console.WriteLine("Thread {0} terminé : début {1:hh:mm:ss}, durée programmée {2} s, fin {3:hh:mm:ss}, durée effective {4}",
                    tâches[i].Name,data[i].Début,data[i].Durée,data[i].Fin,(data[i].Fin-data[i].Début));
            }        
            // Ende der Hauptschleife
            Console.WriteLine("Fin du thread {0} à {1:hh:mm:ss}", main.Name, DateTime.Now);
        }

        public static void Sleep(object infos) {
            // Der Parameter wird abgerufen
            Data data = (Data)infos;
            // Wartezeit von „Durée“ Sekunden
            Thread.Sleep(data.Durée*1000);
            // Ende der Ausführung
            data.Fin = DateTime.Now;
        }
    }

    internal class Data {
        // Verschiedene Informationen
        public DateTime Début { get; set; }
        public int Durée { get; set; }
        public DateTime Fin { get; set; }
    }
}

      • Fin: Startzeitpunkt der Thread-Ausführung – festgelegt durch den startenden Thread
    • Zeilen 35–43: Die von den Threads ausgeführte Methode Sleep hat die Signatur void Sleep(object obj). Der effektive Parameter obj ist vom Typ [Data], der in Zeile 45 definiert ist.
    • Zeilen 15–22: Erstellung von 5 Threads
    • Zeile 17: Jeder Thread wird der Methode „Sleep“ in Zeile 35 zugeordnet
    • Zeile 21: Ein Objekt vom Typ [Data] wird an die Methode Start übergeben, die den Thread startet. In diesem Objekt wurden der Startzeitpunkt der Thread-Ausführung sowie die Dauer in Sekunden, während der der Thread „schlafen“ soll, vermerkt. Dieses Objekt wird im Array in Zeile 14 gespeichert.
    • Zeilen 24–30: Der Thread [Main] wartet auf das Ende aller von ihm gestarteten Threads.
    • Zeilen 28–29: Der Thread [Main] ruft das Objekt data[i] vom Thread Nr. i ab und zeigt dessen Inhalt an.
    • Zeilen 35–42: Die von den Threads ausgeführte Methode Sleep
    • Zeile 37: Der Parameter vom Typ [Data] wird abgerufen

    10.5. Paralleler Zugriff auf gemeinsam genutzte Ressourcen

    10.5.1. Nicht synchronisierter paralleler Zugriff

    Im Abschnitt über den Informationsaustausch zwischen Threads wurden die Informationen nur zwischen zwei Threads und zu ganz bestimmten Zeitpunkten ausgetauscht. Dabei handelte es sich um eine klassische Parameterübergabe. Es gibt andere Fälle, in denen eine Information von mehreren Threads gemeinsam genutzt wird, die diese möglicherweise gleichzeitig lesen oder aktualisieren möchten. Dabei stellt sich das Problem der Integrität dieser Information. Nehmen wir an, die gemeinsam genutzte Information sei eine Struktur S mit verschiedenen Informationen I1, I2, … In.

    • Ein Thread T1 beginnt mit der Aktualisierung der Struktur S: Er ändert das Feld I1 und wird unterbrochen, bevor er die vollständige Aktualisierung der Struktur S abgeschlossen hat.
    • Ein Thread T2, der nun die Prozessorausführung übernimmt, liest daraufhin die Struktur S, um Entscheidungen zu treffen. Er liest eine Struktur in einem instabilen Zustand: Einige Felder sind auf dem neuesten Stand, andere nicht.

    Diese Situation wird als Zugriff auf eine gemeinsam genutzte Ressource – in diesem Fall die Struktur S – bezeichnet und ist oft recht schwierig zu handhaben. Betrachten wir das folgende Beispiel, um die Probleme zu veranschaulichen, die dabei auftreten können:

    • Eine Anwendung generiert n Threads, wobei n als Parameter übergeben wird
    • Die gemeinsam genutzte Ressource ist ein Zähler, der von jedem erzeugten Thread erhöht werden muss

    10.5.3. Die Klasse „Mutex“

    Auch die Klasse System.Threading.Mutex ermöglicht es, kritische Abschnitte abzugrenzen. Sie unterscheidet sich von der lock-Klausel hinsichtlich der Sichtbarkeit:

    • Die `lock`-Klausel ermöglicht die Synchronisation von Threads derselben Anwendung
    • Die Mutex-Klasse ermöglicht die Synchronisation von Threads verschiedener Anwendungen.

    Wir werden den folgenden Konstruktor und die folgenden Methoden verwenden:

    public Mutex()
    erstellt ein Mutex M
    public bool WaitOne()
    Der Thread T1, der die Operation M.WaitOne() ausführt, fordert die Eigentumsrechte am Synchronisationsobjekt M an. Wenn das Mutex M von keinem Thread gehalten wird (was zu Beginn der Fall ist), wird es dem Thread T1 „übergeben“, der es angefordert hat. Wenn wenig später ein Thread T2 dieselbe Operation ausführt, wird er blockiert. Denn ein Mutex kann nur einem Thread gehören. Er wird freigegeben, sobald der Thread T1 den von ihm gehaltenen Mutex M freigibt. So können mehrere Threads in Erwartung des Mutex M blockiert sein.
    public void ReleaseMutex()
    Der Thread T1, der die Operation M.ReleaseMutex() ausführt, gibt den Besitz des Mutex Mutex M ab. Wenn der Thread T1 die Prozessorsteuerung verliert, kann das System diesen an einen der auf den Mutex M wartenden Threads vergeben. Nur einer erhält ihn seinerseits, während die anderen, die auf M warten, blockiert bleiben

    Ein Mutex M verwaltet den Zugriff auf eine gemeinsam genutzte Ressource R. Ein Thread fordert die Ressource R über M.WaitOne() an und gibt sie über M.ReleaseMutex() zurück. Ein kritischer Codeabschnitt, der jeweils nur von einem einzigen Thread ausgeführt werden darf, ist eine gemeinsam genutzte Ressource. Die Synchronisation der Ausführung des kritischen Abschnitts kann wie folgt erfolgen:

    M.WaitOne();
// Nur dieser Thread darf hier eintreten
// kritischer Abschnitt
....
M.ReleaseMutex();

    10.5.4. Die Klasse AutoResetEvent

    Ein Objekt AutoResetEvent ist eine Barriere, die jeweils nur einen Thread durchlässt, genau wie die beiden vorherigen Werkzeuge lock und Mutex. Ein Objekt AutoResetEvent wird wie folgt erstellt:

    AutoResetEvent barrière=new AutoresetEvent(bool état);

    Der Boolesche Wert état gibt an, ob die Schranke geschlossen (false) oder geöffnet (true) ist. Ein Thread, der die Schranke passieren möchte, gibt dies wie folgt an:

    barrière.WaitOne();
    • Ist die Barriere offen, passiert der Thread sie und die Barriere wird hinter ihm wieder geschlossen. Wenn mehrere Threads gewartet haben, ist sichergestellt, dass nur einer durchkommt.
    • Ist die Barriere geschlossen, wird der Thread blockiert. Ein anderer Thread wird sie zu gegebener Zeit öffnen. Dieser Zeitpunkt hängt vollständig von der zu lösenden Aufgabe ab. Die Barriere wird durch den folgenden Befehl geöffnet: 
    barrière.Set();

    Es kann vorkommen, dass ein Thread eine Barriere schließen möchte. Dies kann er mit folgendem Befehl tun:

    barrière.Reset();

    10.6. Paralleler Zugriff auf mehrere gemeinsam genutzte Ressourcen

    10.6.1. Ein Beispiel

    In unseren vorherigen Beispielen wurde eine einzige Ressource von den verschiedenen Threads gemeinsam genutzt. Die Situation kann sich komplizieren, wenn es mehrere Ressourcen gibt und diese voneinander abhängig sind. Insbesondere kann es zu einer Deadlock-Situation kommen. Diese Situation, die auch als deadlock bezeichnet wird, liegt vor, wenn zwei Threads gegenseitig aufeinander warten. Betrachten wir die folgenden, zeitlich aufeinanderfolgenden Aktionen:

    • Ein Thread T1 erlangt die Kontrolle über einen Mutex M1, um Zugriff auf eine gemeinsam genutzte Ressource R1 zu erhalten
    • Ein Thread T2 erlangt die Kontrolle über einen Mutex M2, um auf eine gemeinsam genutzte Ressource R2 zugreifen zu können
    • Der Thread T1 fordert den Mutex M2 an. Er wird blockiert.
    • Der Thread T2 fordert den Mutex M1 an. Er wird blockiert.

    Hier warten die Threads T1 und T2 gegenseitig aufeinander. Dieser Fall tritt auf, wenn Threads zwei gemeinsam genutzte Ressourcen benötigen: die Ressource R1, die durch den Mutex M1 gesteuert wird, und die Ressource R2, die durch den Mutex M2 gesteuert wird. Eine mögliche Lösung besteht darin, beide Ressourcen gleichzeitig mithilfe eines einzigen Mutex M anzufordern. Dies ist jedoch nicht immer möglich, wenn dies beispielsweise zu einer langen Blockierung einer ressourcenintensiven Ressource führt. Eine andere Lösung besteht darin, dass ein Thread, der über M1 verfügt und M2 nicht erhalten kann, daraufhin M1 freigibt, um eine gegenseitige Blockierung zu vermeiden.

    1. Es gibt ein Array, in das Threads Daten schreiben (die Schreiber) und andere diese lesen (die Leser).
    2. Die Schreiber sind untereinander gleich, aber exklusiv: Es kann jeweils nur ein Schreiber seine Daten in das Array schreiben.
    3. Die Leser sind untereinander gleich, schließen sich jedoch gegenseitig aus: Es kann jeweils nur ein Leser die im Array abgelegten Daten lesen.
    4. Ein Leser kann die Daten aus dem Array nur lesen, wenn ein Schreiber sie dort abgelegt hat, und ein Schreiber kann nur dann neue Daten in das Array schreiben, wenn die darin enthaltenen Daten von einem Leser gelesen wurden.

    Man kann zwei Arten von gemeinsam genutzten Ressourcen unterscheiden:

    • die schreibbare Tabelle: Es darf jeweils nur ein Schreiber darauf zugreifen.
    • die Lese-Tabelle: Es darf jeweils nur ein Leser darauf zugreifen.

    sowie eine Reihenfolge für die Nutzung dieser Ressourcen:

    • Ein Leser muss immer erst nach einem Schreiber kommen.
    • Ein Schreiber muss immer erst nach einem Leser kommen, außer beim ersten Mal.

    Der Zugriff auf diese beiden Ressourcen kann mit zwei Barrieren vom Typ AutoResetEvent gesteuert werden:

    • Die Sperre peutEcrire kontrolliert den Zugriff der Schreiber auf die Tabelle.
    • Die Schranke peutLire wird den Zugang der Leser zur Tafel kontrollieren.
    • Die Schranke peutEcrire wird zunächst in geöffneter Position angelegt, sodass ein erster Autor passieren kann, während alle anderen zurückgehalten werden.
    • Die Barriere peutLire wird zunächst geschlossen angelegt, wodurch alle Leser blockiert werden.
    • Sobald ein Schreiber seine Arbeit beendet hat, öffnet er die Schranke peutLire, um einen Leser hereinzulassen.
    • Wenn ein Leser seine Arbeit beendet hat, öffnet er die Barriere peutEcrire, um einen Schreiber hereinzulassen.

    10.6.2. Die Klasse „Monitor“

    Im vorherigen Beispiel:

    • gibt es zwei gemeinsam genutzte Ressourcen zu verwalten
    • Für eine bestimmte Ressource sind die Threads gleichberechtigt.

    Wenn die Schreib-Threads bei der Anweisung peutEcrire.WaitOne blockiert sind, wird einer von ihnen – egal welcher – durch die Operation peutEcrire.Set freigegeben. Wenn die vorherige Operation die Barriere für einen bestimmten Schreib-Thread öffnen soll, wird die Sache komplizierter.

    Man kann dies mit einer Einrichtung vergleichen, die an Schaltern Kunden empfängt, wobei jeder Schalter auf einen bestimmten Bereich spezialisiert ist. Wenn der Kunde eintrifft, zieht er am Ticketautomaten eine Wartemarke für Schalter X und setzt sich dann hin. Jede Wartemarke ist nummeriert, und die Kunden werden über einen Lautsprecher anhand ihrer Nummer aufgerufen. Während der Wartezeit kann der Kunde tun, was er möchte. Er kann lesen oder ein wenig dösen. Er wird jedes Mal durch den Lautsprecher geweckt, der ankündigt, dass die Nr. Y am Schalter X aufgerufen wird. Wenn er gemeint ist, steht der Kunde auf und begibt sich zum Schalter X, andernfalls macht er weiter mit dem, was er gerade getan hat.

    Hier kann man analog vorgehen. Nehmen wir das Beispiel der Schriftsteller:

    plusieurs écrivains attendent pour un même guichet
    Ihre Threads sind blockiert
    le guichet se libère et le n° de l'écrivain suivant est appelé
    Der Thread, der das Array im Lesemodus verwendet hat, teilt den Schreib-Threads mit, dass das Array verfügbar ist. Er oder ein anderer Thread hat den Schreib-Thread festgelegt, der die Barriere passieren muss.
    chaque écrivain regarde son n° et seul celui qui a le n° appelé
va au guichet. Les autres se remettent en attente.
    Jeder Thread prüft, ob er der Ausgewählte ist. Wenn ja, passiert er die Barriere. Wenn nicht, wartet er weiter.

    Die Klasse „Monitor“ ermöglicht die Umsetzung dieses Szenarios.

    Wir beschreiben nun eine Standardkonstruktion (pattern), die im Kapitel Threading des in der Einleitung dieses Dokuments erwähnten Buches „C# 3.0“ vorgestellt wird und in der Lage ist, Probleme mit Barrieren mit Zugangsbedingungen zu lösen.

    • Zunächst greifen die Threads, die sich eine Ressource (den Schalter, …) teilen, über ein Objekt darauf zu, das wir als „Token“ bezeichnen. Um die Barriere zu öffnen, die zum Schalter führt, benötigt man das Token, und es gibt nur ein einziges Token. Die Threads müssen sich das Token daher untereinander weitergeben. 
    object jeton=new object();
    • Um zum Schalter zu gelangen, fordern die Threads zunächst das Token an: 
    Monitor.Enter(jeton);

    Ist der Token frei, wird er dem Thread zugewiesen, der den vorherigen Vorgang ausgeführt hat; andernfalls wird der Thread in die Warteschlange für den Token gestellt.

    • Erfolgt der Zugang zum Schalter ungeordnet, c.a.d. Ist es unerheblich, wer als Nächstes hereinkommt, reicht der vorherige Vorgang aus. Der Thread, der das Token besitzt, begibt sich zum Schalter. Erfolgt der Zugang geordnet, prüft der Thread, der das Token besitzt, ob er die Bedingung für den Gang zum Schalter erfüllt: 
    while (! jeNeSuisPasCeluiQuiEstAttendu) {Monitor.Wait(jeton);}

    Ist der Thread nicht derjenige, der am Schalter erwartet wird, gibt er seine Reihe ab, indem er das Token zurückgibt. Er wechselt in einen blockierten Zustand. Er wird wieder aktiviert, sobald das Token für ihn wieder verfügbar ist. Dann prüft er erneut, ob er die Bedingung für den Gang zum Schalter erfüllt. Die Operation Monitor.Wait(Token), die das Token freigibt, kann nur ausgeführt werden, wenn der Thread Eigentümer des Tokens ist. Ist dies nicht der Fall, wird eine Ausnahme ausgelöst.

    • Der Thread, der die Bedingung für den Gang zum Schalter prüft, begibt sich dorthin:
    1. // Arbeit am Schalter
    2. ....

    10.7. Thread-Pools

    Bisher haben wir zur Verwaltung von Threads:

    • haben wir sie mit „Thread T = new Thread(...)“ erstellt
    • und anschließend mit T.Start() ausgeführt

    Im Kapitel „Datenbanken“ haben wir gesehen, dass es bei bestimmten SGBD möglich ist, Pools mit offenen Verbindungen zu nutzen:

    • n-Verbindungen werden beim Start des Pools geöffnet
    • Wenn ein Thread eine Verbindung anfordert, erhält er eine der offenen Verbindungen aus dem Pool
    • Wenn der Thread die Verbindung schließt, wird sie nicht geschlossen, sondern an den Pool zurückgegeben

    Die Verwendung eines Verbindungspools ist auf Codeebene transparent. Der Vorteil liegt in der Leistungssteigerung: Das Öffnen einer Verbindung ist ressourcenintensiv. Hier können 10 geöffnete Verbindungen Hunderte von Anfragen bedienen.

    Ein ähnliches System gibt es für Threads:

    • min Threads werden beim Start des Pools erstellt. Der Wert von min wird mit der Methode ThreadPool.SetMinThreads(min1,min2) festgelegt. Ein Thread-Pool kann zur Ausführung von blockierenden oder nicht blockierenden, sogenannten asynchronen Aufgaben verwendet werden. Der erste Parameter min1 legt die Anzahl der blockierenden Threads fest, der zweite min2 die Anzahl der asynchronen Threads. Die aktuellen Werte dieser beiden Parameter können mit ThreadPool.GetMinThreads(out min1,out min2) abgerufen werden.
    • Ist diese Anzahl nicht ausreichend, erstellt der Pool weitere Threads, um die Anfragen bis zur Obergrenze von max Threads zu bedienen. Der Wert von max wird mit der Methode ThreadPool.SetMaxThreads(max1,max2) festgelegt. Die beiden Parameter haben dieselbe Bedeutung wie in der Methode SetMinThreads. Die aktuellen Werte dieser beiden Parameter können über ThreadPool.GetMaxThreads(out max1,out max2) abgerufen werden. Sobald die Anzahl der Threads gemäß max1 erreicht ist, werden Thread-Anforderungen für blockierende Aufgaben in die Warteschlange gestellt, bis ein freier Thread im Pool verfügbar ist.

    Ein Thread-Pool bietet verschiedene Vorteile:

    • Wie beim Verbindungspool wird Zeit bei der Erstellung von Threads eingespart: 10 Threads können Hunderte von Anfragen bedienen.
    • Die Anwendung wird abgesichert: Durch die Festlegung einer maximalen Anzahl von Threads wird verhindert, dass die Anwendung durch zu viele Anfragen überlastet wird. Diese werden in eine Warteschlange gestellt.

    Um einem Thread aus dem Pool eine Aufgabe zuzuweisen, verwendet man eine der beiden folgenden Methoden:

    1. ThreadPool.QueueWorkItem(WaitCallBack)
    2. ThreadPool.QueueWorkItem(WaitCallBack, object)

    wobei WaitCallBack eine beliebige Methode mit der Signatur void WaitCallBack(object) ist. Methode 1 weist einen Thread an, die Methode WaitCallBack auszuführen, ohne ihr einen Parameter zu übergeben. Methode 2 tut dasselbe, übergibt jedoch einen Parameter vom Typ object an die Methode WaitCallBack.

    10.8. Die Klasse BackgroundWorker

    10.8.1. Beispiel 1

    Die Klasse BackgroundWorker gehört zum Namensraum [System.ComponentModel]. Sie wird wie ein Thread verwendet, weist jedoch Besonderheiten auf, die sie in bestimmten Fällen interessanter machen können als die Klasse [Thread]:

    • Sie löst die folgenden Ereignisse aus:
    • DoWork: Ein Thread hat die Ausführung von BackgroundWorker angefordert
    • ProgressChanged: Das Objekt BackgroundWorker hat die Methode ReportProgress ausgeführt. Diese dient dazu, einen Ausführungsgrad in Prozent anzugeben.
    • RunWorkerCompleted: Das Objekt BackgroundWorker hat seine Arbeit beendet. Dies kann normal, durch Abbruch oder aufgrund einer Ausnahme geschehen sein.

    Diese Ereignisse machen das Objekt BackgroundWorker in grafischen Benutzeroberflächen nützlich: Eine lang andauernde Aufgabe wird einem BackgroundWorker übertragen, das mit dem Ereignis ProgressChanged über seinen Fortschritt und mit dem Ereignis RunWorkerCompleted über seinen Abschluss berichten kann. Die vom BackgroundWorker auszuführende Arbeit erfolgt über eine Methode, die dem Ereignis DoWork zugeordnet wurde.

    • Es ist möglich, die Abbruch der Aufgabe zu veranlassen. In einer grafischen Benutzeroberfläche kann eine lang andauernde Aufgabe somit vom Benutzer abgebrochen werden.
    • Die Objekte BackgroundWorker gehören zu einem Pool und werden nach Bedarf wiederverwendet. Eine Anwendung, die ein Objekt BackgroundWorker benötigt, erhält dieses aus dem Pool, der ihr einen bereits vorhandenen, aber ungenutzten Thread zuweist. Die Wiederverwendung von Threads anstelle der jedes Mal neu erstellten Threads verbessert die Leistung.

    10.9. Thread-lokale Daten

    10.9.1. Das Prinzip

    Betrachten wir eine dreischichtige Anwendung:

    Nehmen wir an, es handelt sich um eine Mehrbenutzeranwendung, beispielsweise eine Webanwendung. Jeder Benutzer wird von einem ihm zugewiesenen Thread bedient. Der Lebenszyklus des Threads verläuft wie folgt:

    1. Der Thread wird erstellt oder aus einem Thread-Pool angefordert, um eine Anfrage eines Benutzers zu bearbeiten.
    2. Wenn diese Anfrage Daten erfordert, führt der Thread eine Methode der Schicht [ui] aus, die eine Methode der Schicht [metier] aufruft, die wiederum eine Methode der Schicht [dao] aufruft.
    3. Der Thread gibt die Antwort an den Benutzer zurück. Anschließend wird er beendet oder in einen Thread-Pool zurückgeführt.

    Bei Vorgang 2 kann es sinnvoll sein, dass der Thread über eigene Daten verfügt, c.a.d, die nicht mit anderen Threads geteilt werden. Diese Daten könnten beispielsweise zu dem bestimmten Benutzer gehören, den der Thread bedient. Diese Daten könnten dann in den verschiedenen Schichten [ui, metier, dao] verwendet werden.

    Die Klasse Thread ermöglicht dieses Szenario dank einer Art privatem Wörterbuch, in dem die Schlüssel vom Typ LocalDataStoreSlot sind:

    erstellt einen Eintrag im privaten Wörterbuch des Threads für den Schlüssel name.
    ordnet den Wert data dem Schlüssel name im privaten Wörterbuch des Threads zu
    ruft den Wert ab, der dem Schlüssel name im privaten Wörterbuch des Threads zugeordnet ist

    Ein Anwendungsbeispiel könnte wie folgt aussehen:

    • Um ein Paar (clé,valeur) zu erstellen, das dem aktuellen Thread zugeordnet ist: 
    Thread.SetData(Thread.GetNamedDataSlot("clé"),valeur);
    • Um den Wert abzurufen, der mit clé verknüpft ist: 
    Thread.GetData(Thread.GetNamedDataSlot("clé"));

    Später entsteht für eine andere Anwendung der Bedarf, eine in einer Liste gespeicherte Artikelliste zu löschen, ebenfalls im Rahmen einer Transaktion. Es zeigt sich, dass die Schicht [dao] immer umfangreicher wird, um unterschiedlichen geschäftlichen Anforderungen gerecht zu werden. Man kann einen anderen Weg einschlagen:

    • in die Schicht [dao] nur die grundlegenden Operationen InsertArticle, DeleteArticle, UpdateArticle, SelectArticle und SelectArticles
    • die Vorgänge zur gleichzeitigen Aktualisierung mehrerer Artikel in die Schicht [métier] auslagern. Diese würden die elementaren Vorgänge der Schicht [dao] nutzen.

    Der Vorteil dieser Lösung besteht darin, dass dieselbe Schicht [dao] unverändert mit verschiedenen Schichten [metier] verwendet werden könnte. Sie bringt jedoch eine Schwierigkeit bei der Verwaltung der Transaktion mit sich, die atomar durchzuführende Aktualisierungen an der Datenbank zusammenfasst:

    • Die Transaktion muss von der Schicht [metier] initiiert werden, bevor diese die Methoden der Schicht [dao] aufruft
    • die Methoden der Schicht [dao] müssen über das Vorhandensein der Transaktion informiert sein, um daran teilzunehmen, falls diese existiert
    • Die Transaktion muss von der Schicht [métier] beendet werden.

    Damit die Methoden der Schicht [dao] erkennen, ob möglicherweise eine Transaktion läuft, könnte man die Transaktion als Parameter zu jeder Methode der Schicht [dao] hinzufügen. Dieser Parameter erscheint dann in der Signatur der Methoden der Schnittstelle, wodurch diese an eine bestimmte Datenquelle gebunden wird: die Datenbank. Die lokalen Daten des Threads bieten uns eine elegantere Lösung: Die Schicht [métier] speichert die Transaktion in den lokalen Daten des Threads, und genau dort holt die Schicht [dao] sie ab. Die Signatur der Methoden der Schicht [dao] muss daher nicht geändert werden.

    Implementierung der Schicht [metier]

    Die Fachimplementierung der Schnittstelle IMetier sieht wie folgt aus:

    
using System.Collections.Generic;
using System.Data;
using System.Data.SqlServerCe;
using System.Threading;

namespace Chap8 {
    public class Metier : IMetier {
        // Schicht [dao]
        public IDao Dao { get; set; }
        // Verbindungszeichenfolge
        public string ConnectionString { get; set; }

        // Einfügen einer Artikeltabelle in eine Transaktion
        public void InsertArticlesInTransaction(Article[] articles) {
            // Die Verbindung zur Datenbank wird hergestellt
            using (SqlCeConnection connexion = new SqlCeConnection(ConnectionString)) {
                // Verbindung wird geöffnet
                connexion.Open();
                // Transaktion
                SqlCeTransaction transaction = null;
                try {
                    // Transaktion starten
                    transaction = connexion.BeginTransaction(IsolationLevel.ReadCommitted);
                    // Die Transaktion wird im Thread gespeichert
                    Thread.SetData(Thread.GetNamedDataSlot("transaction"), transaction);
                    // Artikel werden eingefügt
                    foreach (Article article in articles) {
                        Dao.InsertArticle(article);
                    }
                    // Transaktion wird bestätigt
                    transaction.Commit();
                } catch {
                    // Transaktion wird rückgängig gemacht
                    if (transaction != null)
                        transaction.Rollback();
                }
            }
        }

        // Einfügen einer Artikelliste ohne Transaktion
        public void InsertArticlesOutOfTransaction(Article[] articles) {
            // Einfügen der Artikel
            foreach (Article article in articles) {
                Dao.InsertArticle(article);
            }
        }

        // Artikelübersicht
        public List<Article> GetAllArticles() {
            return Dao.GetAllArticles();
        }
        // Alle Artikel löschen
        public void DeleteAllArticles() {
            Dao.DeleteAllArticles();
        }
    }
}

    10.9.3. Fazit

    Das vorangegangene Beispiel hat den Nutzen von thread-lokalen Daten für die Transaktionsverwaltung aufgezeigt. Es sollte nicht unverändert nachgebildet werden. Frameworks wie Spring, NHibernate usw. nutzen diese Technik, machen sie jedoch noch transparenter: Die Schicht [metier] kann Transaktionen verwenden, ohne dass die Schicht [dao] davon Kenntnis haben muss. Es gibt also kein Transaction-Objekt im Code der Schicht [dao]. Dies wird mithilfe einer Proxy-Technik namens AOP (Aspect-Oriented Programming) erreicht. Auch hier kann man dem Leser nur empfehlen, diese Frameworks zu verwenden.
